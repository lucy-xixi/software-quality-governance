# Software Quality & Governance Dashboard

A policy-driven software quality governance framework that connects automated testing, code coverage, static-analysis evidence, quality gates, risk assessment, release readiness, and governance actions.

The project demonstrates how software quality evidence can be transformed into a traceable governance decision rather than treated as isolated engineering metrics.

---

## Project Overview

Software quality governance requires more than measuring test coverage or code quality.

This project implements a governance workflow that:

* collects measurable software quality evidence;
* evaluates quality metrics against explicit governance policies;
* distinguishes **PASSED**, **FAILED**, and **UNAVAILABLE** evidence;
* identifies measured quality risks;
* determines release readiness based on available required evidence;
* generates machine-readable and human-readable governance reports;
* presents governance results through a Streamlit dashboard;
* integrates with GitHub Actions and provides a SonarQube analysis workflow.

The dashboard is a **presentation layer**. Governance decisions are generated by the project-level governance engine and stored in `governance_report.json`.

```text
                             │

                             │
                  ┌──────────┴──────────┐
                  ▼                     ▼
             Risk Assessment     Release Readiness
                  │                     │
                  └──────────┬──────────┘
                             ▼
                   Governance Actions
                             │
                             ▼
                 governance_report.json
                             │

```

### Key design principle

```text
Governance Engine
        ↓
governance_report.json
        ↓
Streamlit Dashboard
```

The dashboard does not independently re-evaluate governance policy. This helps maintain consistency between the governance report and its presentation.

## Quality Governance Model

The project uses an explicit policy defined in:

```text
config/quality_policy.yaml
```

Current policy thresholds include:

| Metric                   |   Policy |
| ------------------------ | -------: |
| Test Coverage            |    ≥ 80% |
| Critical Bugs            |        0 |
| Major Bugs               |        0 |
| Critical Vulnerabilities |        0 |
| High Vulnerabilities     |        0 |
| Duplication              |     ≤ 5% |
| Quality Gate             | Required |

The policy is separated from the implementation so that governance thresholds can be reviewed and changed without rewriting the governance engine.

## Governance Decision Logic

The governance engine distinguishes between three important states:

```text
PASSED
FAILED
UNAVAILABLE
```

### UNAVAILABLE is not zero

If a required metric has not been collected, the project does **not** assume that its value is zero.

For example:

```text
Vulnerabilities = UNAVAILABLE
```

does not mean:

```text
Vulnerabilities = 0
```

This distinction is important for release governance because the absence of evidence should not automatically be interpreted as evidence of quality.

---

## Quality Gate

The project-level quality gate evaluates the configured policy against available evidence.

The current governance flow is:

```text
Coverage
   ↓
Required SonarQube Evidence
   ↓
Overall Quality Gate
   ↓
Release Readiness
```

A passing individual metric does not automatically make the release ready.

For example, the current project has:

```text
Coverage:          81.69%
Policy minimum:    80%
Coverage status:   PASSED

SonarQube evidence: UNAVAILABLE

Quality Gate:       FAIL
Release Readiness:  NOT_READY
Risk:               UNASSESSED
```

The result is driven by the governance policy and evidence availability, not by an assumption that unavailable metrics have passed.

---

## Release Readiness

Release readiness is evaluated separately from individual quality metrics.

The project currently requires:

1. required governance evidence to be available;
2. required policy conditions to pass;
3. no measured blocking condition.

Therefore:

```text
Coverage PASSED
        +
Required evidence UNAVAILABLE
        ↓
Quality Gate FAIL
        ↓
Release Readiness NOT_READY
```

This demonstrates the difference between **metric-level quality** and **release-level governance**.

---

## Risk Assessment

Risk is assigned to **measured policy failures**.

The project uses the following risk hierarchy:

```text
LOW
MEDIUM
HIGH
CRITICAL
```

Unavailable evidence is not automatically assigned a risk level.

Therefore, when required SonarQube-derived evidence is unavailable:

```text
Risk = UNASSESSED
```

rather than treating unavailable evidence as a confirmed defect.

## Governance Reporting

The governance engine generates two report formats:

```text
reports/
├── governance_report.json
└── governance_report.md
```

### JSON report

`governance_report.json` is the machine-readable source used by the Streamlit dashboard.

It contains:

* project identity;
* quality gate result;
* release readiness;
* risk;
* coverage;
* bug evidence;
* vulnerability evidence;
* duplication evidence;
* code-smell evidence;
* policy conditions;
* failed conditions;
* unavailable conditions;
* recommended governance actions.

### Markdown report

`governance_report.md` provides a human-readable governance summary suitable for review and audit-oriented workflows.

## SonarQube Integration

The repository includes:

```text
sonar-project.properties
```

and a GitHub Actions workflow configured for SonarQube analysis.

The intended workflow is:

```text
GitHub Actions
      ↓
Automated Tests
      ↓
Coverage Artifact
      ↓
SonarQube Analysis
      ↓
SonarQube Quality Gate
```

The repository also distinguishes between:

### Project-level governance policy

Implemented by:

```text
src/governance.py
```

and reported through:

```text
reports/governance_report.json
```

### SonarQube server-side quality gate

Evaluated by the SonarQube server after an actual analysis.

These are related but intentionally not treated as the same decision mechanism.

### Current limitation

An actual SonarQube server-side analysis has **not yet been executed in this repository**.

Therefore, the dashboard does not fabricate SonarQube values.

Current SonarQube-derived evidence is displayed as:

```text
UNAVAILABLE
```

until an actual analysis provides the corresponding measurements.

* SonarQube Evidence;
* Quality Gate Conditions;
* Release Readiness explanation;
* Risk Assessment;
* Recommended Governance Actions;



## Limitations and Scope

This project intentionally does **not** claim capabilities that have not been implemented or executed.

The current repository does not provide actual:

* Black Duck scan results;
* Coverity scan results;
* SBOM generation results;
* OSS license compliance results;
* enterprise vulnerability database results;
* SonarQube server-side scan results.

These capabilities can be integrated as future governance evidence sources.

The current implementation instead demonstrates the governance architecture, policy evaluation, evidence handling, reporting, dashboard presentation, automated testing, and CI/CD integration.

## Governance Principles Demonstrated

This project is built around several principles:

### 1. Policy-driven

Quality thresholds are explicitly defined rather than embedded throughout the application.

### 2. Traceable

Governance decisions can be traced back to policy conditions and measured evidence.

### 3. Evidence-based

The system distinguishes measured results from unavailable evidence.

### 4. No false certainty

Missing evidence is not automatically interpreted as a passing result.

### 5. Separation of concerns

The governance engine evaluates policy; the dashboard presents the resulting report.

### 6. Release-oriented

The objective is not simply to display metrics, but to support structured release-readiness assessment.
